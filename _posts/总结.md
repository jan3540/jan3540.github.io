项目背景：

​    公司原客服体系基于企业微信人工客服，随着咨询量增长，公司启动智能客服平台建设。基于 Dify + 大语言模型构建企业知识库问答系统，实现多渠道接入，并负责系统容器化部署、Kubernetes 运维、CI/CD 自动化发布及监控体系建设。

- 自动化数据同步：编写Python脚本，优化数据预清洗与文本切片，有效降低了向量处理负载，Dify平均响应耗时从20s缩减至10s以内，性能提升近100%。

- Dify工作流与渠道接入：搭建Dify工作流，创建飞书机器人应用，实现用户咨询入口与自动问答接入。

k8s v1.17升级至v1.28踩坑点

在将 Kubernetes 从 1.17 升级到 1.28 的过程中，核心问题可以归纳为 **四大类：API 变更、运行时变化、网络组件问题、系统兼容性问题**。

### 📊 K8s 1.17 → 1.28 升级核心避坑指南

| **涉及版本/组件**    | **❗ 故障现象 / 报错特征**                                    | **🎯 核心本质 (Root Cause)**                                  | **✅ 终极解决对策 (Action)**                                  |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **CRI 切换 (1.18+)** | `no such file /var/run/docker.sock`                          | Kubelet 不会自动识别 containerd                              | 启动参数强制指定 `containerd.sock`                           |
| **1.24 大更新**      | Kubelet 启动失败： `unknown flag: --network-plugin` `dockershim not found` | 1.24 彻底移除了底层 dockershim 代码； 强制废弃了旧版网络插件传参模式。 | 清理 `/var/lib/kubelet/kubeadm-flags.env` 中所有包含 `docker` 和 `network-plugin` 的历史参数。 |
| **Calico**           | 节点 `NotReady` CoreDNS 频繁超时/重启                        | 旧版 Calico 调用的 v1beta1 API 被高版本 K8s 废弃； 节点存在多个 CNI 配置残影。 | 1. 严格按兼容矩阵提前升级 Calico。 2. 极端情况清理 `/etc/cni/net.d/` 并 `iptables -F`。 |
| **1.28 终极演进**    | systemd 报错： `unknown command unix:///...`                 | 高版本移除了大部分命令行 Flag，导致 systemd 把参数值当成了系统命令执行。 | **全面转向配置文件驱动：** 清空命令行 flag，将配置全部写入 `/var/lib/kubelet/config.yaml`。 |

> **💡 核心工程建议：** 跨度极大的升级，优先选择 **“新增高版本节点 → 驱逐旧节点 Pod (Drain) → 下线旧节点”** 的轮替模式，而非在原节点上原地升级，可规避 90% 的历史配置残留风险。

> Jenkinsfile:
>
> ```shell
> pipeline {
>     agent any
>     environment {
>         gitRepoUrl    = 'ssh://git@192.168.20.200:2222/root/test.git'
>         harborUser    = 'admin'
>         harborPasswd  = 'Harbor12345'
>         harborAddress = '192.168.20.200:5000'
>         harborRepo    = 'repo'
>     }
>     stages {
>         stage('拉取 Git 指定 Tag 代码') {
>             steps {
>                 checkout([
>                     $class: 'GitSCM',
>                     branches: [[name: "refs/tags/${params.tag}"]],
>                     userRemoteConfigs: [[
>                         url: "${env.gitRepoUrl}",
>                         credentialsId: 'gitlab-ssh'
>                     ]]
>                 ])
>             }
>         }
>         stage('构建 Docker 镜像') {
>             steps {
>                 sh """
>                 docker build -t ${harborAddress}/${harborRepo}/${JOB_NAME}:${params.tag} .
>                 """
>             }
>         }
>         stage('推送镜像到 Harbor') {
>             steps {
>                 sh """
>                 echo ${harborPasswd} | docker login -u ${harborUser} --password-stdin ${harborAddress}
>                 docker push ${harborAddress}/${harborRepo}/${JOB_NAME}:${params.tag}
>                 """
>             }
>         }
>         stage('替换 k8s yaml 中的 tag 变量并放入 /tmp') {
>             steps {
>                 sh """
>                 sed "s/\\\${tag}/${params.tag}/g" /root/test/kubernetes/deployment.yaml > /tmp/deployment.yaml
>                 """
>             }
>         }
>         stage('K8s 远程部署与重启服务') {
>             steps {
>                 sh """
>                 scp /tmp/deployment.yaml root@192.168.20.250:/root/test/kubernetes/deployment.yaml
>                 ssh root@192.168.20.250 cat /root/test/kubernetes/deployment.yaml
>                 ssh root@192.168.20.250 'KUBECONFIG=/etc/kubernetes/admin.conf kubectl apply -f /root/test/kubernetes/deployment.yaml'
>                 ssh root@192.168.20.250 'KUBECONFIG=/etc/kubernetes/admin.conf kubectl rollout restart deployment ${JOB_NAME}'
>                 """
>             }
>         }
>     }
> }
>

如何清洗：

对表格的数据进行切片，并转为大模型友好的makedown语言，每个问题一个切片



如何实现响应速度的提升：

1.以前需要手动上传文档，平台有150+的文档库和知识库，每篇300-500个字，上传和更新很麻烦，同时有失效的文档链接/知识库在里面，没有对这些失效的知识库做更新，导致dify光在知识库检索环节就花了10-15秒，针对这个，我新增了平台文档协同表，结构为文档名，文档链接，分类，失效链接，状态，以平台文档链接的形式传入dify知识库，大幅度减少减少速度
